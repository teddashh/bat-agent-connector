# Explicit desktop updates

The native Settings panel checks one fixed GitHub release feed, reviews one candidate,
downloads and verifies its bytes, then requires a separate Install action. The browser
has no update command. The WebView cannot choose URLs, keys, file paths or installer
arguments. Default CI packages contain no updater public key and visibly disable updates.

The official Tauri updater 2.13.2 verifies Minisign signatures and requires the signed
version to equal the announced version. Only a newer Windows x64 NSIS version is eligible.
The native adapter overrides endpoints, target and headers, disables proxy inheritance,
limits redirects to GitHub asset origins and caps downloads at 128 MiB and 185 seconds.
The feed also identifies API 1, contract `2026-10-08`, source SHA and canonical workflow.
These feed metadata fields are descriptive; the signature binds artifact bytes and version,
not the feed's source/workflow assertions. Release tooling derives those from the reviewed
checkout. A corrupted or relabelled download never becomes installable.

Check failures preserve the original candidate. A cached verified download can restore
the Install state without another network request. Rechecking successfully replaces that
candidate. All mutation commands serialize; candidate IDs prevent stale buttons from
installing a replacement. Only local Status is allowed during an in-flight command.

Install validates verified bytes before stopping local connections. Quit and updates share
one lifecycle guard. The original Fleet ticket is invalidated before shutdown, and the
native Launcher/Monitor guards remain held through the installer call. Only positively
owned local processes may be stopped. Unknown ownership or an active launcher refuses.
An app which has never had Fleet configuration can update without inventing a supervisor.
Central tasks and remote BAT processes continue independently.

Before invoking the installer, Rust durably creates a receipt under `update-intents`,
keyed by the source binary version. It records candidate, target version, source SHA and
artifact digest. An unreadable, partial or existing receipt blocks another installation
attempt. A lost reply or process restart reads the original receipt; it cannot resend.
The old binary keeps local launches fenced and opens Settings for recovery. A newly
installed binary has a different version epoch; the old receipt remains historical.
Installer launch/exit is not proof that installation succeeded. A refusal before intent
creation can be reviewed again after Fleet ownership is resolved.

## Release preparation

The ordinary `desktop` workflow builds **unsigned validation packages**. The manually
invoked `desktop-signed-candidate` workflow only builds and uploads an updater-signed
candidate; it never creates a release, publishes a feed, installs an app or restarts a host.
Its exact 40-character source SHA must already belong to main. Version comes from the
committed Tauri config; canonical workflow comes from the same checkout's skill.

The repository owner supplies a `desktop-release` environment with an independently
backed-up signing identity: public `DESKTOP_UPDATER_PUBLIC_KEY` variable and
`TAURI_SIGNING_PRIVATE_KEY` / optional `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` secrets.
Private signing keys are not generated by this implementation or stored in the repository.
Keep the public key stable across releases; changing it requires a separately planned
transition for installed clients. Increment the committed app version for each release.

The `update_manifest` Rust example verifies the actual installer bytes and signature
against that public key and requires exactly the committed signed version before writing
`dashboard-update.json`. A temporary key, wrong key, changed bytes or relabelled version
cannot silently produce a valid feed for another installation identity. Upload the
reviewed `.exe`, `.exe.sig` and JSON together to the matching `v<version>` release only
after installed acceptance; the application reads the latest release's JSON. The workflow
has only read repository permission, so publication remains an explicit operator action.

Updater signing and Windows Authenticode are separate. This workflow does not claim a
trusted Windows publisher certificate or SmartScreen reputation. Authenticode must be
configured in the release environment before it is claimed as part of a distributed build.
See [Tauri updater signing](https://v2.tauri.app/plugin/updater/) and
[Windows signing](https://v2.tauri.app/distribute/sign/windows/).

## Evidence and remaining acceptance

Tests use ephemeral in-memory keys and loopback HTTP peers with the real Tauri verifier:
valid download, changed bytes, missing/mismatched signed version, cached recovery, original
receipt after reopen, and partial receipt refusal. The release verifier rejects altered
bytes, wrong keys and ambiguous signed versions. No fixture invokes an installer.
Shared UI tests cover both languages at 390/768/1440, disabled unsigned builds, explicit
actions and lost-reply recovery. Native final-effect tickets have separate queue/quit tests.

Packaged Windows stop/install/reopen, signing-environment execution, real release feed
publication and installed version readback remain acceptance gates. Linux packages do not
offer this Windows installer flow. Fixture/CI results are not installed/live evidence.
